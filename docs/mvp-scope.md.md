# SignalForge — MVP Scope

**Status:** Approved by Ayush on 2026-09-24 — scaffolding may proceed; database models still need their own review doc.
**Date:** 2026-09-24

## 1. One-line summary

SignalForge is a small, opinionated API reliability platform: a Python API sends it
request telemetry, and it answers four questions — which endpoint regressed, when it
began, how severe the user impact is, and whether a deploy coincided with the change.

## 2. Primary user

A developer responsible for 1–5 HTTP services who can read raw logs today but cannot
quickly answer the four questions above — and for whom Datadog/New Relic are too
expensive and self-hosted stacks (SigNoz, HyperDX) are too operationally heavy.

## 3. MVP scope (8 weeks, ~2h/day)

### In scope

1. **Project & API-key management** — create a project, get an API key, revoke/rotate it.
2. **Python middleware SDK** — drop-in middleware (Django/Flask-style) that records
   per-request telemetry and ships it in batches. Must never slow down or break the
   host app if SignalForge is down.
3. **Batched event ingestion** — `POST /v1/ingest` accepting a JSON array of events;
   auth by API key; dedupe by `event_id`; queue-backed so traffic spikes don't lose data.
4. **Rollup workers** — aggregate events into fixed time windows per
   (project, service, endpoint): request count, error count/rate, p50/p95/p99 latency.
5. **Dashboards** — per-endpoint latency percentiles, request rate, error rate over time.
6. **Endpoint SLOs + burn-rate view** — declare targets (e.g. "99% success, p95 < 300ms"
   over a 30-day rolling window); show remaining error budget and burn rate.
7. **Baseline anomaly detector** — flags unusual endpoint behavior and shows its
   evidence (baseline vs. observed, sample trace IDs, nearby deploys). No black-box scores.
8. **Trace drill-down + deploy annotations** — click an anomaly, see sample requests;
   mark deploys on the timeline to eyeball correlation.

### Non-goals (explicitly out of the MVP)

- Replacing Datadog/Grafana/OpenTelemetry collectors
- OpenTelemetry ingestion, arbitrary logs, or infrastructure metrics
- SDKs for other languages (Python only)
- Alert routing (email/Slack/PagerDuty) — in-app anomaly list only
- Automatic remediation or "AI root cause" claims
- Multi-region collectors, billing, enterprise compliance

### MVP promise (the only thing we guarantee)

For **one instrumented Python service**: endpoint latency, traffic, errors, SLO status,
traces, deploy markers, and explainable anomaly evidence — on one dashboard.

## 4. Telemetry event contract (the core of this doc)

This is the schema the SDK sends and the ingest API accepts. Everything downstream
(rollups, SLOs, anomalies) is derived from these fields, so changes here are expensive —
review carefully.

### 4.1 Request event
_________________________________________________________________________________________________________________________________
| Field         | Type        | Required |                                      Notes                                           |
|---------------|-------------|----------|--------------------------------------------------------------------------------------|
| `event_id`    | string (UUID v4)| yes  | Generated by the SDK; used for dedup on retry.                                       |
| `project_id`  | string      | yes      | Resolved server-side from the API key; SDK does not send it.                         |
| `service`     | string      | yes      | Logical service name, e.g. `"animeverse-api"`. Set once in SDK config.               |
| `timestamp`   | string (ISO-8601, UTC) | yes | When the request completed, recorded by the SDK.                               |
| `method`      | string      | yes      | HTTP method, uppercased: `"GET"`, `"POST"`, …                                        |
| `route`       | string      | yes    | **Route template, not the raw path.**`/api/anime/{id}`,never `/api/anime/42`. See §4.3.|
| `status_code` | integer     | yes      | HTTP status returned to the client.                                                  |
| `duration_ms` | number      | yes      | Server-side handling time, milliseconds, ≥ 0.                                        |
| `trace_id`    | string      | yes      | SDK-generated per request; lets the dashboard drill from an aggregate into samples.  |
| `error_type`  | string      | no       | Only when `status_code >= 500`: exception class name, e.g. `"IntegrityError"`.       |
| `error_msg`   | string      | no       | Only when `status_code >= 500`: truncated to 500 chars, no stack traces in MVP.      |
| `sdk_version` | string      | yes      | e.g. `"0.1.0"` — lets us evolve the contract later.                                  |
_________________________________________________________________________________________________________________________________


Deliberately **excluded** from the MVP: request/response bodies, headers, user IDs, IPs.
(Privacy by omission — we don't want PII anywhere near the event store.)

### 4.3 Cardinality rule (important)

`route` must be a **template**. If the SDK sends raw paths (`/api/anime/1`, `/api/anime/2`,
…), every distinct ID becomes its own dashboard row and the rollups explode. The SDK
normalizes using the framework's route patterns (Django: `request.resolver_match.route`;
fallback: best-effort templating, documented as a known limitation).

### 4.4 SDK batching & failure behavior

- The SDK buffers events in memory (bounded: default 1,000 events).
- Flush when the buffer hits 100 events **or** every 10 seconds, whichever comes first.
- Flush is a single `POST /v1/ingest` with a JSON array body, authenticated by API key header.
- On failure: exponential backoff retry (3 attempts). If the buffer is full, **drop oldest** —
  the host app's performance always wins over telemetry completeness.
- If SignalForge is unreachable for an extended period, the SDK degrades silently
  (one log line at startup/warning level, then quiet). It must be impossible for the SDK
  to take down the host app.

### 4.5 Ingest API guarantees

- `POST /v1/ingest`: auth via `X-API-Key` header → resolves `project_id`.
- Validation: accept valid events, return per-index errors for invalid ones (never lose
  good data because of one bad event).
- Dedupe on `event_id` per project (idempotent retries from the SDK are expected).
- Respond `202 Accepted` fast; actual aggregation happens asynchronously in workers.
- Out-of-order / late events (clock skew): accepted if `timestamp` is within the last
  24h, else rejected. Late events still count toward their original window.

## 5. Data & retention

- **Raw request events:** kept 7 days (enough for trace drill-down; keeps storage bounded).
- **Rollup windows:** 1-minute and 1-hour aggregates per (project, service, endpoint),
  kept 90 days. Dashboard reads rollups, never raw events, except drill-down.
- **Deploy events:** kept indefinitely (tiny).

## 6. SLO & anomaly definitions (MVP)

- **SLO (per endpoint):** success-rate target (default 99%) + optional p95 latency target
  (default 500ms), evaluated over a rolling 30-day window.
- **Error budget:** `100% − target`; **burn rate** = (current error rate ÷ budgeted error rate).
  Dashboard shows: budget remaining %, burn rate over last 1h and 6h.
- **Anomaly detector (baseline, explainable):** per (endpoint, 15-min time-of-day bucket),
  maintain median and MAD (median absolute deviation) of latency and error rate over the
  trailing 14 days. Flag when the current 5-min window deviates > 4×MAD for 3 consecutive
  windows. Each flag stores its evidence: baseline median/MAD, observed values, sample
  `trace_id`s, and any deploy within ±30 min.

## 7. Settled decisions

1. **Ingest validation:** accept-valid / reject-invalid per event.
2. **Rollup windows:** 1-min + 1-hour.
3. **Stack:** Django + DRF + PostgreSQL + Redis queue.
4. **First instrumented service:** real AnimeVerse backend.
5. **Raw-event retention:** 7 days.

## 8. Success criteria (how we know the MVP works)

- [ ] SDK installed on one service; dashboard shows p50/p95/p99, rate, errors per endpoint.
- [ ] Ingest survives a 10× traffic spike without data loss or dashboard lag (load test).
- [ ] Duplicate retries don't corrupt rollups (dedupe test).
- [ ] An SLO breach and a real latency regression are both visible with correct burn-rate math.
- [ ] The anomaly detector flags an injected regression with attached evidence, and stays
      quiet for a week of normal traffic (false-positive check).
- [ ] Deployed live with a demo project + seeded data a stranger can click through.
